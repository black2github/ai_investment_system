Ответ на вашу проверку §21.1 (имена ключей распределений) по коду `dist_ppf`:
| семейство | движок | схема v1.0 | итог |
|---|---|---|---|
| triangular | min / mode / max | то же | ок |
| pert | min / mode / max, optional `lambda` (по умолчанию 4.0) | min / mode / max | **добавить optional `lambda`** |
| truncated_normal | mean / **sd** / min / max (min и max optional, по умолчанию ±∞) | mean / **sigma** / min / max | **схема → `sd`**; min/max — optional |
| lognormal | median / sigma | то же | ок |
| deterministic | value | то же | ок |
По вашему же правилу «схему под движок, а не движок под схему»: ключ `sd`, не `sigma`. Движок не трогаем.

## 2. Решения по вашим находкам §17 и §15
2.1 **state_transition_effects (§17).** Принимаем вашу семантику v2: калибровка соответствует подтверждённому текущему
    вектору состояний; после подтверждённого перехода калибровка обновляется новой версией до следующего
    нормативного прогона. Движок под «спящие» сдвиги не расширяем. Условные сдвиги SPCX v1.0 (C1→C2, C2→C3, D3→D4)
    переносятся в Markdown-обоснование калибровки v1.1 как документированные ожидания, не в YAML.
2.2 **not_mapped (§15).** Принимаем: material-драйвер без поддерживаемой цели = отказ G5, waiver не вводим. Если в
    B/C такой драйвер встретится — назвать его в пояснении и предложить цель или аргумент нематериальности.
2.3 **C1 (размытие как reduced-form proxy)** — принято; параметр `dilution_penalty` = model_assumption с обоснованием,
    чувствительность к нему — в robustness_tests для архетипа C.
