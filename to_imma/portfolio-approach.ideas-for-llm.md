# Блок для передачи другой LLM (ChatGPT-проект «Инвестиционный портфель 2026»)

Вставляется одним сообщением от строки «=== НАЧАЛО ===» до «=== КОНЕЦ ===». Цель: чтобы следующие
артефакты сразу переносились в работающий дозор на OpenClaw без переделки.

=== НАЧАЛО ===

Ниже — состояние работающей системы мониторинга (OpenClaw + агент invest) на 20.09.2026 и просьбы
к следующим артефактам. Прошу учитывать это как ограничения и как уже принятые решения, а не как
предложения для пересмотра.

## A. Что уже работает и не подлежит переделке

1. Реестр триггеров на компанию `portfolio/<тикер>/triggers.yaml`: `id` вида `<ТИКЕР>-<P|F|E|X|C>-NN`
   (P — вход по цене, F — фиксация, E — подтверждение тезиса, X — что ломает тезис, C — даты),
   поля `class` (price | calendar | event | digest), `step` (шаг маршрута), `condition` (с числом),
   `source`, `action` (текст запроса решения владельцу), `window`, `automation`, `status`
   (active | planned | due | idea | done | dropped), `notes`. Блок `route.steps` — маршрут компании
   (степпер), `kind: stage | scenario`.
2. Состояние `state.json`: `fired` (сработавшие триггеры со `status: pending_owner`), `events_reported`
   (подтверждённые события с источником и `confirmation: strong|weak`), `pending_verification`
   (факты со `status: unverified|verified|mismatch|not_found`, `actual_value`, `source_url`),
   `owner_decision` + `decided_at` у закрытых пунктов, `route.current`, `info_log` (справочные события).
3. Лист идей `portfolio/_ideas.yaml`: `watch` / `ideas` (с `return_condition`) / `rejected`, цены на
   дату идеи. Сценарий `portfolio/_scenarios/taiwan.yaml` со стадиями S1–S3 и признаками наступления.
4. Автоматизации: ценовые сторожа (скрипт без LLM, срабатывание только при смене зоны; справочные
   события не тревожат сразу), новостной дозор 09:00 МСК, проверки по отчётам в даты отчётов, вечерняя
   сводка 20:00 «ждёт решения», карточка компании по запросу тикера. Модель проверок — Claude Sonnet;
   источники: только первоисточники (SEC, IR, релизы) или два СМИ первого ряда; котировки — Yahoo
   chart (цена и валюта; капитализации и мультипликаторов в этом источнике нет).
5. Правила сообщений: первая строка `AG: invest, ID: <id>` или `ЗАДАЧА: <имя>`; строка «Где мы» (шаг
   маршрута и прогресс); действие дословно из реестра с пояснением терминов; «Решение за владельцем»;
   только по-русски, без иероглифов, термины пояснять; справочное — в сводку, а не сразу.
6. Принципы: триггер ≠ решение (агент не торгует, только Decision Request); факт ≠ новость (проверка
   по первоисточнику до записи); реестр правится раньше автоматизаций; ничего не удаляется молча —
   устаревшее помечается legacy/dropped с причиной.

## C. Просьбы к следующим артефактам

1. **SPCX State Vector в формате реестра.** Для пяти осей (AI compute, Starlink, Starship,
   капиталоёмкость, valuation) выдать YAML `states.yaml`: для каждой оси — список состояний с кодами
   (A0…A4 и т.д.), для каждого перехода — условия с числом, периодом («два квартала подряд» и т.п.),
   источником проверки и уровнем события E1/E2/E3. Каждому переходу — `trigger_id` в нашем формате
   `SPCX-E-NN` (новые номера начиная с SPCX-E-10; существующие E-01…E-09 не переименовывать, а
   привязать к осям полем `axis`). Текущее состояние по каждой оси на 20.09.2026 с evidence и ссылкой.
2. **KPI Dashboard SPCX** как YAML `kpis.yaml`: KPI, единица, период, источник, формула, пороги
   Green/Yellow/Red числом, последнее значение с датой и ссылкой. Не более 10 критических KPI.
3. **Decision Request** как шаблон сообщения, совместимый с нашим форматом (первая строка
   `AG: invest, ID: <trigger_id>`, «Где мы», «Состояние: <ось> <from> → <to>», «Почему: факт + ссылка»,
   «Влияние на портфель: …», «→ варианты решения: держать / увеличить / сократить / ждать / выйти»,
   «Решение за владельцем»). Без таблиц: Telegram их не показывает.
4. **Схема портфеля** `_portfolio.yaml` (позиции, количество, валюта, кэш/резерв, NAV по датам,
   целевые веса, ограничения из §28 и §30 Constitution) и **определения просадок** в машинном виде
   (окно 12 месяцев для акции, максимум NAV для портфеля, индекс для сектора) — чтобы наш скрипт мог
   считать их из цен без LLM.
5. **Контракт расчётного движка**: входной JSON (состояния по осям, диапазоны допущений на состояние,
   цены, позиции, ограничения, seed, версия модели) и выходной JSON (median CAGR 3/5/8Y, P(2x), P(5x),
   downside, max drawdown, дисперсия сценариев, Persistence Ratio, implied price/CAGR, предложенные
   веса, тесты устойчивости и концентрации). Движок будет реализован скриптами на Python вне LLM;
   от вас нужны формулы и допущения, а не расчёты.
6. **Согласование вселенной.** Явно указать статус каждой из уже отслеживаемых бумаг в вашей
   иерархии: SPCX, NET, CRWD, SU, ETN, Yaskawa (6506), Harmonic Drive (6324) — Core / Challenger /
   Candidate / Discovery / вне вселенной, с причиной. И наоборот: для Core-10 и челленджеров, которых
   в дозоре нет, — минимальный Event Map с датами ближайших отчётов и 3–5 числовыми триггерами, в
   нашем формате реестра.
7. **Пометки legacy**: какие из существующих триггеров (ценовые цели сценариев A/B/C SpaceX, уровни
   фиксации по капитализации, действия по стадиям сценария «Тайвань») считать legacy до появления
   valuation-модели. Не удалять, а пометить.
8. Форматные требования ко всем артефактам: по-русски (термины с пояснением), названия документов
   на других языках не копировать; каждая цифра-предпосылка со ссылкой; YAML, а не таблицы в тексте;
   идентификаторы в наших форматах.
