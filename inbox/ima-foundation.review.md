# Investment Modeling Agent v1.0 Foundation — разбор со стороны конвейера (2026-09-22)

Источник: share 6ab22e7c (6 сообщений от вопроса владельца о формализации роли), пакет
`Downloads/Investment_Modeling_Agent_v1.0_foundation` (24 файла, PACKAGE_MANIFEST с sha256).
Статус пакета: proposed_normative; в workspace НЕ принят (лежит в Downloads).

## 1. Вывод

Направление верное и совпадает с тем, как конвейер уже работает де-факто: LLM выпускает кандидата →
детерминированная конвертация и слияние в реестры владельца → дозор сверяет по первоисточникам → patch.
Пакет описывает ТОЛЬКО половину конвейера — сторону LLM. Вторая половина (интегратор, дозор, движок) в нём
названа одним словом («deterministic gates», «dosor_or_equivalent»), а именно там в этой сессии была вся
ручная работа. Принимать пакет как норматив рано: не хватает четырёх документов и одной предпосылки
(снимки workspace под git). Список ниже.

## 2. Что упущено (по убыванию важности)

1. **Нет схемы конечных артефактов (Company Artifact Schema).** Манифест вводит измерение
   `artifact_schema_version`, но в пакете нет самого документа: формат `states.yaml / kpis.yaml /
   triggers.yaml / mpc_inputs.yaml / state.json` workspace. Без него IMA-07 («yaml_parses,
   schema_refs_resolve») и гейт G5 непроверяемы. Факт из сессии: формат ответа LLM плыл от партии к партии
   (партия 5 потребовала отдельный конвертер), и «компиляцию» делал не LLM, а наш конвертер
   (`_apply_batch.py` → `_apply_merge.py`). Значит, IMA-07 в реальности исполняет система, а не LLM —
   это надо либо признать (IMA-07 = детерминированный шаг интегратора), либо дать LLM целевую схему.
2. **Нет Source Policy как отдельного норматива.** IMA-02 и G2 ссылаются на `source_policy` как на вход,
   но документа нет. У нас правила разбросаны: `source_policy` внутри kpis.yaml каждой компании,
   правила SEC User-Agent и усечения web_fetch — в AGENTS.md дозора. Нужен один дом: разрешённые
   источники и их приоритет (SEC > IR > стенограммы > агрегаторы только для цены), обязательный `as_of`,
   правило «guidance ≠ actual», допуски сверки.
3. **Протокол дозора (G8) не специфицирован.** Две проверки «source_values_verified, discrepancies_closed»
   — это не контракт. Реально дозор принимает kpis с `source_url/verified/last_value`, воспроизводит число
   из документа, возвращает расхождения; часть сверок (NVDA 10-Q, партия 3) пришлось делать на хосте
   (SEC 403 без UA, OpenRouter 402). Нужен формат отчёта сверки (per-KPI: found / mismatch / not_found /
   period_mismatch, с цитатой и URL) и правило, что EvidencePack LLM должен быть потребляем дозором
   (единый формат evidence_item — он в пакете есть, но дозор о нём не знает).
4. **Авторитет присвоения ID не определён.** Пакет требует «existing_ids_preserved», но в сессии главная
   работа была в обратную сторону: LLM предлагает свои ID (KPI, драйверы, common_cause), система назначает
   канонические (E-ids, binding map в `_apply_merge.py`). Нужно явно: LLM выпускает локальные ID,
   канонические присваивает интегратор при слиянии; PatchProposal ссылается на канонические.
   Иначе IMA-13 (patch/migration) не построить.
5. **Golden cases не машиночитаемы.** `expected_behavior` — прозаические строки. Для автоматической оценки
   нужны утверждения вида «путь в артефакте → ожидаемый типизированный результат» (например
   `kpis.NBIS-KPI-xx.value_type == company_guidance`). Плюс предпосылка: «snapshot до исправления» взять
   неоткуда — workspace не под git. Это наше действие: завести git в workspace-invest до первого
   conformance-прогона.
6. **Загрязнение conformance-эксперимента.** Автор принятых моделей — тот же ChatGPT-проект с памятью.
   Прогон «воспроизведи NBIS без принятого результата» на нём не измеряет переносимость. Исполнителем
   первого прогона должна быть другая модель (через OpenRouter в OpenClaw: Sonnet 5 / DeepSeek), а ChatGPT —
   независимый рецензент (IMA-08), что как раз соответствует `review_policy.independent_model_preferred`.
7. **Транспорт в Model Adapter.** Сейчас адаптер для ChatGPT — это файл заказа в `inbox/`, share-ссылка,
   папка Downloads и конвертер на хосте. Adapter Contract должен содержать транспорт задачи и результата
   (ручной share / cron-сообщение агенту / API), иначе Invocation/Result envelope существуют только на
   бумаге. Наш формат заказов (`inbox/*.request.md`) надо выровнять с Skill_Runtime_Envelope.
8. **Детерминированные гейты G0–G5 без исполнителя.** Естественный дом — модель `artifact_validator` в
   реестре invest-calc (версия попадает в `calculation_engine_version`). Начать с G5 (schema + ID +
   references) — дешевле всего, у нас уже есть конвертеры. Без реализации гейтов пакет остаётся
   документацией.
9. **Production manifest у 14 принятых моделей отсутствует.** Ретроспективно заполнить при слиянии
   (produced_by: ChatGPT/share-ссылка/партия, хеши входов, дата сверки) — дёшево добавить в `_apply_merge`.
10. Мелочи: нет схемы Decision Request для `OWNER_DECISION_REQUIRED` (у нас решения владельца живут в
    STATUS.md и журнале убеждения); нет понятия «партия» (batch из 2–3 компаний) — envelope на задачу;
    `skip_states_allowed: false` не совместим с IMA-03..08 без web (там EVIDENCE_COLLECTED снаружи —
    нужно состояние EVIDENCE_PROVIDED).

## 3. Где не согласен / предостережение

- Риск переформализации: 24 контракта против 14 моделей, сделанных неформальным процессом за три дня.
  Ценность появится только с исполняемыми гейтами и одним живым прогоном. Порядок: git в workspace →
  схема артефактов → G5-валидатор → conformance NBIS на чужой модели. Остальные документы пакета до
  этого не трогать.
- IMA-09..11 (RV/MC/Joint) откладывать не нужно: схема калибровки v2 уже зафиксирована движком
  (company_mc 2.3.0: joint_simulation, driver_parameter_mapping, архетип C в milestone_mc). Контракт
  IMA-10 — это просто ссылка на эту схему с указанием `calculation_engine_version`. Заказ MC v1.1 +
  калибровок NBIS/NVDA после Flight 14 можно оформить как первый живой вызов IMA-10 в формате envelope.
