## 3. Dozor Verification Protocol v1.0 — принят для KPI, два уточнения к v1.1
Соответствует заказу: 11 статусов на KPI, различение not_found / not_disclosed / source_unavailable_technical,
допуски (half-ULP, 0.1% для derived), период как часть факта, guidance как mismatch_semantics, JSON Schema отчёта,
правила мутации (дозор не переписывает канонические KPI/условия/ID). Реализуем на нашей стороне: раздел сверки в
AGENTS.md дозора по протоколу, хранение отчётов, режим валидатора для отчётов дозора по встроенной схеме.
Уточнения, которые нужны в v1.1 (не блокируют внедрение v1.0):
3.1 **Область сверки.** Протокол покрывает только KPI. В фактических заходах дозор сверял ещё два класса:
    (а) текущие состояния осей — `state.json → scenario_state[axis].verified` (факты, поддерживающие current
    из states.yaml, включая качественные оси с evidence_type=qualitative_primary_source); (б) события для
    E-/X-триггеров (новости, отчёты) по Source Policy (правило двух first-tier media). Нужны статусы и правила
    для этих двух классов в том же отчёте (секции `axis_items`, `event_items`) или отдельными протоколами.
3.2 **Место хранения и связь с runtime.** Протокол задаёт схему отчёта, но не говорит, где он лежит и как
    попадает в state.json. Наше предложение (подтвердить или поправить): отчёт — файл
    `portfolio/<ticker>/_verify/<run_id>.json` (иммутабельный, по схеме отчёта), в `state.json` дозор пишет
    только наблюдения `kpi_observations[]` (value, provenance, verified по runtime_verified_mapping,
    `verification_run_id`) и строку в `info_log`; summary.overall_status → поле `state.json.verification`
    {run_id, as_of, overall_status}. Для этого в Artifact Schema понадобятся `kpi_observations[].verification_run_id`
    и `state.json.verification` — просьба включить в v1.0.3 вместе с §4, если согласны с раскладкой.
3.3 Мелочь: `as_of` отчёта задан как date-time; у наших артефактов as_of — дата. Оставляем date-time для отчёта
    (момент прогона), но просьба зафиксировать это явно в пояснении, чтобы не путать с as_of документа-источника.

## 4. Заказ патча v1.0.3: статус `paused` (+ поля из §3.2 при согласии)
Решение владельца 22.09: покупки по legacy-реестрам (NET, ETN, SU, 6506, 6324 — 22 триггера с действием «купить»)
приостановлены до оценки портфеля по методологии; наблюдение цены и событий продолжается, уведомление о покупке
не отправляется. Реестр это выражает так (уже применено):

```yaml
- id: NET-P-01
  status: paused
  note: 'ПАУЗА с 2026-09-22 (решение владельца): покупка по legacy-реестру приостановлена до оценки портфеля по
    методологии; наблюдение цены/событий продолжается, уведомление о покупке не отправляется; прежний статус: active'
```

Просьба в v1.0.3 (поверх v1.0.2, других изменений нет):
1. `triggers[].status` enum: добавить `paused` — условие наблюдается и журналируется, действие не исполняется и
   не уведомляется, обратимо (прежний статус в note). Отличие от `dropped` (окончательно) и `planned` (не взведён).
2. ART-REF-015 (trigger ≠ decision): проверять текст действия только у `active | planned | due`; `paused | dropped |
   done` — не проверять. Наш валидатор уже так делает.
3. Company Candidate Schema не меняется (кандидат статусы не задаёт).
