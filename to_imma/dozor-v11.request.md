## 1. Первый живой прогон по протоколу v1.0 — выполнен
Исполнитель: агент-дозор OpenClaw (Sonnet 5, изолированная сессия, 22.09 23:14–23:17 МСК), компания NBIS, 11 KPI,
три документа Q2 2026 на sec.gov (Exhibit 99.1 релиз, Exhibit 99.2 письмо акционерам, 6-K от 12.08).
Итог: `PASS_WITH_DECLARED_PENDING` — 5 verified_match, 5 verified_match_with_normalization, 1 not_found (KPI-11,
кандидат уже был `null + pending_verification`); PATCH_REQUIRED пуст. Отчёт (вложение) прошёл валидатор по
`output_report_schema` с первого раза; папка после записи state.json — pass по Company Artifact Schema v1.0.3.
Технически: 3 curl с настроенным User-Agent, ни одного 403; ~15 минут; больше всего времени ушло на поиск цитат в
длинных документах (Exhibit 99.2 — 42 тыс. символов без навигации). Golden case «guidance ≠ actual» удержан
(KPI-08 подтверждён как company_guidance). Протокол v1.0 принят в эксплуатацию; ниже — что показал прогон.

## 2. Обратная связь исполнителя (полный текст — вложение dozor-run1.feedback.md)
2.1 **not_found vs not_disclosed при «цель есть, факта нет».** KPI-11 (фактически законтрактованная мощность на
    дату отчёта): документы дают только цель 5 GW на конец 2026 и качественные описания стройки, явного «не
    раскрываем» нет. Исполнитель выбрал not_found (структура раскрытия не доказывает принципиального
    нераскрытия — факт может появиться в следующем отчёте) и просит явный пример в протоколе.
2.2 **Квалификатор источника ≠ квалификатор кандидата при совпавшем числе.** KPI-05: источник «approximately
    $5.7 billion», кандидат `5.7 exact`. Исполнитель дал verified_match (число совпадает буквально, «approximately»
    — округление автора); критерий не прописан.
2.3 **Даты источников.** У `states.sources.*.as_of` стояла дата фиксации ссылки (2026-09-21), а не подачи
    документа. Мы это уже исправили на нашей стороне по EDGAR index (NBIS — 2026-08-12; аналогично ещё 12 моделей),
    as_of теперь = дата подачи, как требует Source Policy. Исполнитель предлагает отдельно хранить момент фиксации
    ссылки (см. §3.4).
2.4 **Состояния осей.** В state.json у 4 из 5 осей `verified: true` без привязки к прогону — это старый, менее
    строгий механизм подтверждения (дозор до протокола). v1.1 должна решить его судьбу.
2.5 **«N кварталов подряд».** Триггеры вида «2 квартала подряд» — где считать счётчик: в отчёте сверки или по
    истории kpi_observations по датам.
2.6 **Диапазон из одной фразы** («50–60%»): проверка «оба конца независимо» должна означать «оба граничных
    значения присутствуют в одной цитате», а не поиск двух цитат.
2.7 Замечание владельца по уведомлениям: статусы в сообщениях владельцу нужны по-русски (оригинал в скобках);
    у нас это уже сделано словарём в инструкции дозора — просьба добавить в протокол поле `label_ru` у каждого
    статуса, чтобы словарь имел один нормативный дом.

## 3. Заказ: Dozor Verification Protocol v1.1
Принцип, который вы предложили и который принят: один отчёт, один run_id, один G8 — расширяем `output_report_schema`,
а не заводим новые протоколы.
3.1 **`axis_items[]`** — подтверждение текущего состояния каждой оси `scenario_state[axis]`: вход — критерий
    состояния из states.yaml (`criteria`, `criteria_provenance`) и KPI/качественные свидетельства, на которых
    оно основано; выход — статус оси (предложение: `state_supported` / `state_not_supported` /
    `state_pending_verification` / `evidence_unavailable_technical` / `evidence_conflict`), ссылки на
    подтверждённые KPI-items того же отчёта или на цитату первоисточника (для `evidence_type:
    qualitative_primary_source`), `runtime_verified` для `scenario_state[axis].verified` и
    `scenario_state[axis].verification_run_id` (поле для Artifact Schema v1.0.4). Правило миграции старого флага:
    `verified: true` без run_id считается «не подтверждено по протоколу» до первого axis_item.
3.2 **`event_items[]`** — события для -E-/-X-триггеров (новости, отчёты, регуляторные решения): статусы
    (предложение: `event_confirmed_primary` / `event_confirmed_two_media` / `event_unconfirmed` /
    `event_contradicted` / `source_unavailable_technical`), правило двух first-tier media при отсутствии
    первичного источника (Source Policy), связь с `state.json.events_reported[]` и `fired[]` (поле
    `verification_run_id`). Trigger ≠ decision сохраняется: event_item подтверждает факт, а не переход и не действие.
3.3 **Правила к статусам KPI:** (а) явный пример для 2.1: «прогноз метрики раскрыт, факт той же метрики на дату
    не упомянут» → какой статус и при каких условиях not_disclosed; (б) квалификатор: при совпавшем числе и
    расхождении только квалификатора (approximate/exact, lower_bound/exact) — предложение: статус
    `verified_match_with_normalization`, в `normalization.steps` запись `qualifier: source=approximate,
    candidate=exact`, `patch_required: false`, но новое поле item `qualifier_patch_suggested: true`, по которому
    интегратор правит форму (не значение) в kpis.yaml; (в) диапазон из одной фразы — одной цитаты достаточно (2.6).
3.4 **Даты:** `as_of` источника = дата подачи/публикации документа (уже так). Просьба добавить в схему источника
    optional `recorded_at` (когда ссылка зафиксирована в реестре) — чтобы два понятия не смешивались, как в 2.3.
3.5 **«N кварталов подряд» (2.5):** предложение — дозор счётчики не считает; отчёт подтверждает наблюдения с
    `period_end`, а условие «подряд» вычисляет детерминированная проверка перехода по истории
    `kpi_observations` (это отдельный механизм оценки переходов, не G8). Просьба зафиксировать это разграничение в
    протоколе одной фразой, чтобы исполнитель не пытался считать сам.
3.6 **`label_ru`** у статусов KPI/осей/событий и у итогов прогона (2.7).
3.7 **Patch v1.0.4 Company Artifact Schema** (минимальный, вместе с v1.1): `scenario_state[axis].verification_run_id`,
    `events_reported[].verification_run_id` / `fired[].verification_run_id`, `sources.*.recorded_at`; Candidate
    Schema без изменений.
Критерии приёмки: схема отчёта v1.1 обратно совместима (отчёт v1.0 из вложения валиден по v1.1 при пустых
axis_items/event_items); все новые статусы имеют семантику, mapping в runtime_verified и правило PATCH/BLOCKED;
пример полного отчёта v1.1 по NBIS (11 KPI + 5 осей + 1 событие) во вложении к ответу.
