## 3. Вход для следующей редакции (не блокирует; вместе с очередными изменениями)
3.1 Переход, условие которого — дискретное событие (NVDA-E-11 «новые экспортные ограничения с раскрытым убытком
    ≥5 % выручки»): в enum transition_checks.result нет «ожидается событие»; исполнитель поставил pending_history с
    оговоркой, хотя истории периодов здесь нет. Просьба: результат pending_event (pending, runtime_verified null,
    обязательная ссылка event_item_refs на event_unconfirmed) либо правило, что такой переход в transition_checks не
    пишется. Предпочитаем первое — один список переходов на отчёт удобнее интегратору.
3.2 Граница condition_not_met для «сторожевых» событийных триггеров: исполнитель верно выбрал event_unconfirmed (10-Q
    молчит), но при таком чтении каждый прогон будет PASS_WITH_DECLARED_PENDING из-за одних и тех же сторожей.
    Возможное правило: для событийного триггера с порогом по раскрытию (≥X % выручки) отсутствие такого раскрытия в
    полном 10-Q за период = condition_not_met за этот период (раскрытие обязательно по существенности).
3.3 found.period записан описательно («Q2 FY2027 (quarter ended 2026-07-26)») при candidate.period «quarterly»:
    семантика совпадает, схема допускает; стоит уточнить, что period — окно (quarterly / LTM / within N days), а
    конкретный интервал — отдельное поле или normalization.steps.
3.4 Содержимое v1.0, перестроенное в v1.1 и не вошедшее в сводную редакцию: допуски нормализации (0.1 % для
    формул, половина последнего знака при округлении), технический доступ (User-Agent, повторы), output_mutation_rules.
    Сейчас эти правила живут в нашей инструкции дозора и Source Policy; просьба в следующей редакции либо вернуть их
    в протокол (kpi_rules / technical_access), либо явно объявить, что их дом — Source Policy.
