## Решения по вашему ответу
1. **Интегратор — принят как отдельная детерминированная роль**, но минимальная. Владелец поднял вопрос
   своевременности: при одной сильной LLM соблюдение формата можно поручить ей, меньше элементов — меньше точек слома.
   Решение: LLM отвечает за формат кандидата (Candidate Schema, строго), интегратор делает только то, что LLM
   делать не может по построению — присвоение канонических ID из текущего состояния реестра, слияние с legacy
   реестром владельца (triggers.yaml с историей срабатываний, state.json с ценами и журналом), идемпотентно.
   Обоснование: эти операции требуют актуального состояния workspace, которого у LLM при ручном транспорте нет;
   передавать ей целые файлы реестра на перезапись — это класс ошибки «молчаливая потеря записи», а не экономия.
   Интегратор уже существует (два скрипта), новых сущностей не создаётся — фиксируется контракт существующей.
2. **Разделение Candidate Schema / Company Artifact Schema — принято.** IMA-07 = Compile Candidate Model Package.
   Слой совместимости со старыми форматами партий 1–5 остаётся миграционным адаптером, новые ответы — только в
   Candidate Schema v1.0.
3. **Иерархия источников по классам с preferred_source_type на тип факта — принята** вместо линейной.
4. **Расширенный набор статусов сверки** (verified_match … not_disclosed / not_found / source_unavailable_technical)
   — принят.
5. **Порядок из вашего §11 — принят** (Artifact Schema → Source Policy + Roles & Seams → валидатор G5 → git-снимок и

## Ограничение объёма: не семь артефактов сразу
Foundation v1.0 состоял из коротких файлов-заготовок (0.5–4.5 КБ). Для схем этого недостаточно: валидатор G5
кодируется по схеме, и каждое поле должно быть определено. Поэтому партиями, каждая проверяется по эталонным
файлам до следующей.

## Партия 1 (этот заказ): Candidate Schema v1.0 + Company Artifact Schema v1.0
Критерии приёмки партии:
- **Полнота по эталону.** Каждое поле, встречающееся в переданных `portfolio_nbis/*` (states.yaml, kpis.yaml,
  triggers.yaml, mpc_inputs.yaml, state.json), должно быть в Artifact Schema классифицировано: required / optional /
  deprecated, тип, enum, кто источник значения (LLM-кандидат | интегратор | дозор в runtime). Поле без классификации
  — дефект партии.
- **Граница кандидата.** Candidate Schema описывает ровно то, что выпускает LLM: локальные ID, оси и состояния,
  KPI с source_ref и provenance, переходы без канонических ID, вектор драйверов, failure modes, `candidate_schema_version`.
  Всё остальное (канонические ID, котировки, route, fired, info_log, calc_runs) — только в Artifact Schema с
  владельцем «интегратор» или «дозор».
- **Ссылочная целостность как список правил** в машиночитаемом виде (для валидатора): переход → ось и оба
  состояния существуют; триггер.kpis → KPI существуют; KPI.source → класс источника из Source Policy; каждое
  материальное число → provenance-тип; `last_value` numeric_or_null; `value_type` actual | company_guidance |
  analyst_estimate.
- **Примеры.** Один полный пример кандидата (NBIS в Candidate Schema, восстановленный из принятой модели) и таблица
  соответствия кандидат → артефакт (какое поле куда переходит при слиянии). Это заодно спецификация интегратора.
- **Формат ответа:** YAML-схемы (JSON Schema внутри YAML допустимо) + один Markdown с пояснениями; все файлы
  проходят парсер; версии в заголовках.
