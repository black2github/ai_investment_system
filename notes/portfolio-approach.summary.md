## 2. Финальный подход (что считать принятым)

**Назначение.** Не «выбрать лучшие акции», а система постоянного обновления портфеля на 8+ лет:
структурная рента → компания, её получающая → количественная оценка → отслеживание тезиса → поиск
новых лидеров → перераспределение. Core — текущий результат работы системы, не постоянный список.

**Горизонты.** 3Y — проверка текущего тезиса; **5Y — главный горизонт оптимизации и Монте-Карло**;
8Y — тест устойчивости (Persistence Ratio = 8Y CAGR / 5Y CAGR); >8Y — только качественно.

**Уровни вселенной.** Discovery (каждые 6 мес) → Candidate → Challenger → Core. Ни у кого нет
пожизненного места в Core. Для каждой Core-компании — свой конкурентный кластер челленджеров.
На момент переписки: Core-10 (AVGO, NVDA, KLAC, ASML, SNPS, CDNS, MSFT, SPCX, RKLB, NBIS),
челленджеры (NET, PLTR, AMD, LRCX, AMAT, INTC, CRWD, META), SU — отдельная «вселенная».
Это данные, не методология; в Constitution явно вынесено «Current Portfolio Target — не часть правил».

**Company Investment Card** (обязательна до Candidate/Challenger/Core): тезис как причинная цепочка
(структурный фактор → bottleneck → рента → KPI → valuation → доходность), драйверы, bottleneck, moat,
структура рынка, **KPI Map** с числовыми порогами Green/Yellow/Red, **Event Map** (событие, дата/окно,
источник, что измеряется, порог, что затрагивает в тезисе, какой параметр модели меняется, реакция),
Valuation Map, **Kill Conditions** (измеримые; не равны автопродаже), карта челленджеров, State
Transition Model, параметры Монте-Карло, роль в портфеле, датированные снапшоты.

**Уровни событий.** E1 — информационное обновление (записать); E2 — пересмотр тезиса (немедленный
review компании, проверить переход состояния); E3 — существенное изменение параметров → новый
Монте-Карло и при необходимости переоптимизация портфеля. Квартальный отчёт — лишь один из источников.

**Определения.** Stock drawdown — от максимума за 12 месяцев; portfolio drawdown — от максимума NAV;
sector drawdown — от максимума индекса сектора; цена покупки не является точкой отсчёта.
Fundamental dislocation — падение ≥20% от reference high при сохранении ≥80% ключевых KPI (не
автосигнал покупки). Broad AI derating — Nasdaq ≥20% и SOX ≥25% просадки, медианная оценка AI-вселенной
−25%, при этом агрегированный рост AI-выручки ≥20%. Semiconductor capex shock — ожидания capex −10%
г/г и ≥2 крупных игрока снижают прогноз. Taiwan shock — определяется наблюдаемыми экономическими
последствиями (перебои производства/судоходства, санкции), не политическим событием.
Макро-режимы Normal / Stress / Shock управляют скоростью использования резерва, но не выбором компаний.

**Сценарный слой (принципы 157–165).**
1. Scenario-first: сценарии — центральный forward-looking слой; Монте-Карло распределяет
   неопределённость внутри сценарного состояния, а не «придумывает будущее».
2. Scenario ≠ State: сценарий — гипотеза о будущем режиме; State — текущая оценка, насколько каждый
   драйвер уже реализуется.
3. **Вектор состояний по осям** вместо Bull/Base/Bear. Для SPCX: A — AI compute (A0…A4), B — Starlink
   (B0…B4), C — Starship (C0…C5), D — капиталоёмкость (D0…D4), E — valuation. Переходы задаются
   измеримыми условиями (например A1→A2: рост AI-выручки >50%, рост contracted sales, высокая
   утилизация, положительная приростная EBITDA).
4. **Trigger → Transition → Decision** — три разных сущности: факт произошёл; система изменила
   состояние; человек принял решение (KEEP / INCREASE / REDUCE / WAIT / EXIT).
5. Монте-Карло условный внутри состояния: состояние задаёт диапазон допущений, MC — разброс внутри.
6. **Decision Traceability**: любое изменение веса объяснимо назад до источника (портфель ← решение ←
   valuation ← сценарий ← переход ← триггер ← факт ← источник).
Артефакт-интерфейс для человека — **Investment State Card**: вектор состояний с цветами, статус тезиса
(N из M условий), главный драйвер, главный риск, ближайшие события, триггеры смены состояния,
портфельный диапазон, «что изменило бы моё мнение», Human Decision: pending.

**Расчётный слой.** «LLM не источник истины для арифметики»: Data → Assumptions → Calculation Engine →
Results → Interpretation. Обязательные выходы: median CAGR 3/5/8Y, P(2x), P(5x), downside, max
drawdown, scenario dispersion, Persistence Ratio; reverse valuation («какое будущее уже в цене»);
оптимизатор портфеля: максимизировать 5Y median CAGR при ограничениях (downside, drawdown, корреляции,
концентрация сценариев); тесты Scenario Robustness и Scenario Concentration; стабильность решения к
допущениям; версии модели (ID, версия, снапшот входов, seed).

**Разделение слоёв хранения.** Methodology (меняется только новой версией Constitution) ≠ Data (факты
с датой и источником) ≠ Interpretation (выводы, могут меняться) ≠ Decision. Приоритет источников:
SEC/официальные filings → IR → официальные материалы → анонсы → качественные вторичные.

**Ещё не определено (Constitution §31, подтверждено владельцем как «принято к проработке»):**
функция оптимизатора; скоринг Core/Challenger; веса return/risk/correlation; методика вероятностей
сценариев; методика изменения вероятностей переходов по KPI; единая downside-метрика; valuation
framework по классам компаний; размеры траншей в Stress/Shock; индивидуальные пороги Event Map;
процедура Discovery; критерии Discovery → Candidate; критерии превосходства Challenger над Core.

## 3. Что другая LLM предложила по интеграции с OpenClaw (реплики 163, 165)

Соответствие: thesis.md = Investment Thesis; triggers.yaml = KPI/Trigger/Event Map (реестр уже есть,
заново не создавать); state.json = Event/State ledger; fired = Trigger Events; pending_verification =
Evidence pending; events_reported = Event Log; owner_decision/pending_owner = Human Decision;
route.current = фаза инвестиционного процесса; price zones = tranche logic; _ideas.yaml = Challenger
registry (Discovery → Watch → Candidate → Challenger → Portfolio; rejected — терминальный).

Принципиальное расхождение: OpenClaw — trigger-driven (событие → триггер → действие → владелец), нужна
state/scenario-driven (событие → факт → KPI → переход состояния → вектор → модель → valuation →
влияние на портфель → решение). Предложение: **не переписывать OpenClaw, сделать его операционным
слоем** (датчики + триггеры + оркестрация), а поверх — Investment State (KPI, вектор, evidence,
переходы), Scenario Engine, Calculation Engine (valuation, MC, портфель), Decision Request → владелец.

Конкретно: (1) в state.json добавить `scenario_state` (по осям) и журнал `state_transitions`
(timestamp, axis, from, to, trigger_id, evidence, confidence); (2) в triggers.yaml у триггеров
добавить `transition: {axis, from, to}` и `decision_context`, поле `action` сохранить как
`action.legacy` для обратной совместимости; (3) отдельно `evidence.status` (unverified/verified) от
`status` триггера; (4) route оставить как фазу, отдельную от вектора состояний компании; (5) старые
ценовые цели A/B/C ($120/$200–250/$350–400) считать legacy до пересчёта valuation-моделью; (6) три
типа триггеров: state-independent (цена), state-dependent (событие), **model-dependent** (implied
CAGR < X, P(loss>30%) > порога, концентрация сценариев) — последние живут в Calculation Engine;
(7) начать с SPCX, инфраструктуру мониторинга почти не трогать; основная работа — формализация
State Vector, Transition Record, Scenario Engine и связи с расчётным слоем.
