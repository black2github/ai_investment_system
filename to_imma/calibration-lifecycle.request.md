триггеры внутри оси в Reverse_Valuation_Rules v1.1 §3 (SPCX E-34…E-37), переходы состояний в triggers.yaml (действие —

одно и то же основание может быть описано по-разному в трёх местах или не описано нигде.

Терминология (просьба владельца, действует для всех русскоязычных текстов): «происхождение» (данных/числа) вместо
«провенанс»; имя поля `provenance` в YAML не меняется. Единицы работы (глоссарий, 25.09): **партия N** — N-я поставка IMMA по одному заказу, нумерация
сквозная для любого содержимого (моделей, калибровок, переизданий, нормативов; «партия 6» = SPOT + ETN v1.0.2, следующая — 7);
**раунд** — полный прогон набора компаний при одном состоянии нормативов; **заход** — повтор портфельной валидации;
**срез** — отдельно принимаемая часть реализации. Просим в пакетах и патч-нотах использовать ту же нумерацию партий.

## Заказ: Calibration_Lifecycle_Rules v1.0 (Markdown + YAML-схема реестра оснований)
1. **Что НЕ является основанием** (только перепрогон): движение цены/капитализации (equity_value_0 — параметр прогона);
   вероятности сценариев, лимиты, режимы (owner_judgment портфельного уровня); результаты Stability/оптимизатора.
2. **Классы оснований** с идентификаторами (CLR-1…), для каждого: кто обнаруживает, какой артефакт затронут (RV | MC |
   оба), какой отклик — патч (дельта) | переиздание (новая версия, полный текст + дельта) | смена архетипа (новая
   структура узлов) | ревалидация без изменения файла:
   - CLR-1 новые факты первоисточников: базовый период (выручка TTM, маржи, баланс, акции, backlog, KPI), корпоративные
     события (конвертируемый долг, допэмиссия, M&A, смена валюты/листинга); срок годности базового периода (предложите
     число кварталов) и обязательная сверка дозором после каждого отчёта; порог материальности расхождения, ниже
     которого патч не нужен;
   - CLR-2 переход состояния по оси (triggers.yaml): какие переходы требуют переиздания, а какие — только патча;
     recalibration-триггеры внутри оси без смены состояния (как SPCX E-34…E-37) — общее правило, не частный случай;
   - CLR-3 смена архетипа (C → B/A при запуске сервиса: ASTS, RKLB; B → A при выходе FCF в плюс: CRWV, NBIS, SPCX):
     признак перехода (например, parity/bridge-диагностика 2 квартала подряд), что сохраняется от старой версии;
   - CLR-4 изменение нормативов и движка: схема калибровки (миграция с ожидаемой migration delta), таксономия
     (новый драйвер → переиздания компаний с экспозицией), Joint-схема (корни/корреляции → **ревалидация всех
     калибровок по MC-G5-013**, потому что измеренная σ зависит от корреляций корней, даже если файлы не менялись),
     пороги правил, семантика движка;
   - CLR-5 реализация failure mode / общей причины (knockout сработал в реальности) — переход в CLR-2/3;
   - CLR-6 обнаруженный дефект калибровки (валидатор, сверка RV↔MC, экспертное замечание) — патч с обоснованием.
3. **Срочность и пакетирование**: что делается немедленно (материальный факт, переход состояния), что — партией
   (миграции, таксономия), правило «один пакет на нормативное изменение».
4. **Версионирование**: патч = +0.0.1, переиздание = +0.1.0 или по вашему правилу; supersedes обязателен; старые прогоны
   остаются записями воспроизводимости (как решено для NBIS/NVDA 1.0.1).
5. **Реестр оснований** (YAML): список CLR-N с полями detector (dozor | triggers | validator | imma | owner), artifact,
   response, urgency — чтобы хост мог механически проверять, что каждое основание имеет отклик.
