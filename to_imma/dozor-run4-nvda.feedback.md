# Обратная связь по прогону 4 (NVDA, первый живой прогон Dozor v1.2) — для v1.2.1

Автор записи: интегратор, по иммутабельному отчёту `portfolio/nvda/_verify/verify-NVDA-20260923T190405Z.json` и его
полям `notes`. Исполнитель (агент-дозор, Sonnet 5, изолированная сессия 23.09 19:04–19:06 UTC) записал отчёт и был
прерван ошибкой биллинга OpenRouter (402: баланс ниже max_tokens запроса) до обновления state.json, собственного
feedback и уведомления владельца; runtime дописан интегратором детерминированно по отчёту.

## Итог прогона
- Отчёт v1.2.0 прошёл валидатор 1.5.0 (схема, DZR-001..016) с первого раза, ~1.63 млн токенов (91% из кэша), 2 минуты.
- 10 KPI: 4 verified_match, 6 verified_match_with_normalization — все derived_fact (KPI-04..08, KPI-10) пересчитаны из
  слагаемых 10-Q в базе кандидата (DZR-012 соблюдён: found = 0.6624 при 63,734/96,221 и т.п.).
- 5 осей state_supported с criterion_checks по KPI отчёта (AI_Demand: «latest-quarter Data Center YoY ≥100%» и
  «2-quarter aggregate ≥100%» — оба true по KPI-02).
- 11 transition_checks: E-01…E-10 not_met (текущий квартал сам опровергает условия «2 квартала подряд»: например,
  E-01 «<100% но ≥50%» при YoY 117%), E-11 pending_history.
- 1 дискретное событие E-11 (новые экспортные ограничения с раскрытым убытком ≥5% квартальной выручки):
  event_unconfirmed по 10-Q (раскрыт charge $0.4B по H200 за H1 — это внутри текущего foreclosure и <5%).
- Итог PASS_WITH_DECLARED_PENDING (только из-за E-11).

## Что показал прогон (вход для v1.2.1)
1. **Переход, условие которого — дискретное событие, а не порог KPI** (E-11: «новые ограничения … произвели
   раскрытый убыток ≥5%»): в enum transition_checks.result нет значения «ожидается событие». Исполнитель поставил
   pending_history с оговоркой в notes, хотя истории периодов здесь нет — нужна либо `pending_event` (pending,
   runtime_verified null, ссылка event_item_refs на event_unconfirmed), либо правило, что такой переход в
   transition_checks НЕ пишется, а его статус целиком определяется event_item. Предлагаем первое: один список
   переходов на отчёт полезен интегратору.
2. **condition_not_met против event_unconfirmed при отсутствии события в первоисточнике.** Исполнитель верно
   выбрал event_unconfirmed (10-Q не утверждает «новых ограничений не было», он молчит), но граница «первоисточник
   положительно показывает, что условие ложно» для событий нуждается в примере в протоколе — иначе каждый прогон
   будет давать PASS_WITH_DECLARED_PENDING из-за одних и тех же «сторожевых» событийных триггеров. Возможное
   правило: для событийного триггера с порогом по раскрытию (≥X% выручки) отсутствие такого раскрытия в полном
   10-Q за период = condition_not_met за этот период (раскрытие обязательно по существенности).
3. **found.period у NVDA записан описательно** («Q2 FY2027 (quarter ended 2026-07-26)») при candidate.period
   «quarterly»: схема допускает, семантика совпадает, но правило сравнения периодов «дословно» стоит уточнить:
   period — окно (quarterly/LTM/within N days), а конкретный интервал — отдельное поле или normalization.
4. Устойчивость исполнения: прерывание после записи отчёта оставило runtime без обновления. Протоколу это не
   противоречит (отчёт иммутабелен и самодостаточен), но полезно закрепить порядок шагов: отчёт → валидатор →
   state.json → feedback → уведомление, чтобы интегратор всегда мог дописать runtime по отчёту (что и сделано).
