## 1. Цель и факты
Парадигма владельца (27.09): действовать заблаговременно — по подтверждённым признакам продвижения сценария, которые видны раньше,
чем цифры в отчётах компаний. Слой распознавания v1.1 принят (каталог событий, scope, критерии фаз, таблица исходов, состояние
сценариев). Не хватает слоя действий: заранее записанной стратегии на сценарий и фазу и связки с числами.
Факты хоста, которые слой действий должен учесть:
- Заход 6: веса оптимума не зависят от вероятностей сценариев (Δ = 0 при ×0.75 / ×1.25 / +10 п.п.) — аллокация зажата
  ограничениями BASE-типа (общая причина TAIWAN_SUPPLY_DISRUPTION 35 %, потолки NVDA/RKLB/SPOT). Вероятности меняют отчётный
  риск (смесь: ES5 +24 % → +2 % у текущих весов), но не веса. Значит, чтобы сценарии влияли на аллокацию, нужны
  сценарно-условные ограничения или явные стратегии по фазам.
- Картины портфеля по сценариям есть (раунды 2–3): под TAIWAN_SEIZURE текущие веса дают +12.6 % / ES5 −32 %, под TAIWAN_QUARANTINE
  +18.6 % / −2 %, под CHIP_COLD_WAR +23.6 % / +26 %; оптимум захода 6 под Тайванем +13.8 % / +3 %.
- Старый слой действий `portfolio/_scenarios/taiwan.yaml` (TAIWAN-S1…S3): действия по бумагам («6324: продать 40 % позиции»,
  «ETN: держать, добавить 10 % портфеля»), перераспределение кэша («50 % → Eaton, 30 % → Schneider, 20 % → кэш»), правило
  сроков («не покупать падение первые 5 торговых дней; после 5 дней, если guidance не снижен >10 % — вернуть половину»). Это
  образец формы; его бумаги (SU, 6506, 6324) частично уже не в портфеле — содержание переписывается под 15 калиброванных бумаг.
- Заход 7 (30.09, после решения владельца по порогам): сценарно-условные ограничения с порогами владельца на оптимуме НЕ
  связывают (под TAIWAN_SEIZURE ES5 +2.5 %, под TAIWAN_QUARANTINE +23.5 %, концентрация 56 %) — они отсекают только портфели
  типа текущего (под Тайванем ES5 −31 %); хедж GLD с плоской доходностью оптимизатор не берёт (кэш под 4 % при том же нулевом
  отклике лучше). Отсюда вопрос 2.7 о модели GLD и вывод: механизм влияния сценариев на веса — стратегии по фазам (часть B).
- Триггер ≠ решение: слой действий выдаёт сигнал владельцу с готовой стратегией; сделок агент не совершает.

## 2. Заказ, часть A: Scenario_Action_Layer_Specification v1.0 + Scenario_Strategy_Schema v1.0
2.1 **Артефакт стратегии** (один файл на сценарий, `portfolio/_scenarios/strategies/<SCENARIO>_strategy_v1.0.yaml`, ссылка из
    `strategy_ref` калибровки на уровне сценария и фазы): для каждой фазы — `phase_strategy` с полями: trigger (фаза
    confirmed по state.json; опционально candidate → «подготовительные» действия), `actions[]` {action_type: reduce | add | hold |
    hedge | cash_target | review; ticker | instrument | «кэш»; magnitude — целевой вес NAV, дельта веса или доля позиции;
    basis: conditional_optimum | owner_rule | legacy; timing — торговые дни после подтверждения, транши, «не покупать падение
    первые N дней»; preconditions — например «guidance не снижен более чем на X %»; provenance: model_assumption |
    owner_judgment; rationale}, `exit_rule` — что делать при exited (разворот / держать / пересмотр), `risk_budget_under_scenario`
    (ES5 и P(loss>30) под сценарием, к которым стратегия приводит портфель), `status` {draft | owner_approved | active |
    executed | retired} с датами; стратегия не может стать active без owner_approved.
2.2 **Условный оптимум как числовое основание** (§21 v1.1): для каждого сценария и фазы хост считает условную картину
    (фаза confirmed → fixed_quarter 0, последующие фазы от неё, probability = 1) и условный оптимум оптимизатора под теми же
    лимитами владельца; стратегия записывает разницу «текущие веса → условный оптимум» как целевые действия с ограничителями
    владельца (максимальный оборот на шаг, транши). Просим: правило, как из условного оптимума получаются действия
    (порог минимального изменения веса, округление, приоритет сокращений над докупками при дефиците кэша), и что стратегия
    фиксируется заранее, а при срабатывании только сверяется с актуальным условным оптимумом (расхождение > X п.п. → пересмотр,
    не автоисполнение).
2.3 **Сценарно-условные ограничения оптимизатора** (Portfolio_Optimizer v1.1 или раздел слоя действий — на ваше усмотрение):
    к существующим risk_5y добавить по каждому adverse-сценарию s с owner-вероятностью p_s ≥ p_min: ES5_5Y(портфель | s) ≥ ES5_min,
    P(loss>30 %)_5Y(портфель | s) ≤ P30_max; ScenarioConcentration ≤ 60 % (вариант «а», только при ≥ 2 adverse-сценариях с
    бременем > 0). **Значения владельца (DR-2026-09-27-01, решение 30.09.2026, owner_judgment): p_min = 0.10; ES5_min = −40 %;
    P30_max = 25 %; концентрация ≤ 60 %; пороги единые для всех сценариев с p ≥ 0.10** (сейчас TAIWAN_SEIZURE 0.10 и
    TAIWAN_QUARANTINE 0.175; CHIP_COLD_WAR 0.07 — вне, но входит в бремя концентрации). Оценка — на scenario-specific наборах
    путей с общими path_id (probability = 1 для сценария, как в §21 v1.1); хост это уже реализовал в движке
    (portfolio_optimizer 1.1.0: жёсткие ограничения в лексикографической схеме §3 без тихого ослабления, концентрация — тай-брейк
    после ES5, когда определена). Просим нормативную формулировку (формула, место в спецификации, порядок относительно потолков /
    общей причины / top-3 / dry powder), правило пересчёта при изменении owner-вероятностей и версию Optimizer (v1.1 — SemVer §13
    Lifecycle: reissue). Расхождения с нашей реализацией — исправим движок под норматив.
2.7 **Инструменты хеджа (В1, решение владельца V1: только кэш и золото GLD, лимит GLD ≤ 10 % NAV; короткие/обратные ETF и
    опционы не разрешены).** У GLD нет калибровки: в оптимизаторе 1.1.0 он — переменная с плоской доходностью 0 % без отклика на
    сценарий (model_assumption), то есть движок видит золото только как не-акционерный балласт, а не как актив, растущий под
    шоком. Просим: (а) нужна ли и какая минимальная модель GLD для слоя действий — рыночный слой (дрейф, волатильность, корреляция
    с драйверами Joint v1.1 и отклик под TAIWAN_*) или оставить плоскую доходность с явной оговоркой; (б) как оформить
    инструмент хеджа в схеме стратегии (instrument_ref, разрешённый список владельца, лимит) и в ACT-правилах.
2.4 **Контракт сигнала и дозора**: (а) дозор: entry/exit_criteria фаз по каталогу событий — как оформлять подтверждение события
    в отчёте дозора (event_items с event_id, observable_criteria по порогам, verified) и переход state.json candidate →
    confirmed → exited; правило ambiguous_set_conflict (подтверждены defining-события разных членов); (б) сигнал агента
    владельцу по §22 v1.1 — русский шаблон в стиле AGENTS.md («AG: invest, СЦЕНАРИЙ: …»: сценарий, фаза, подтверждающие факты и
    источники, условная картина портфеля, стратегия и действия дословно, «Решение за владельцем»); при strategy_ref = null —
    только распознавание; (в) правило пересмотра вероятностей по подтверждённым событиям (связать с DR-2026-09-25-01 п. 5).
2.5 **Правила валидации ACT-001…**: стратегия ссылается на существующие сценарий/фазу; тикеры — из реестра портфеля,
    инструменты хеджа — из списка, разрешённого владельцем; магнитуды в лимитах (потолки на бумагу, кэш по режимам, оборот);
    provenance у каждого числа; статус active только при owner_approved; strategy_ref калибровки указывает на существующую
    стратегию; условный оптимум, на который ссылается стратегия, есть в _runs.
2.6 **Совместимость**: калибровки сценариев не меняются (strategy_ref заполняется патчем v1.1.1 — только ссылки);
    Scenario_State_Schema v1.0 — при необходимости v1.1 с полями исполнения (last_signal_at, strategy_status).
