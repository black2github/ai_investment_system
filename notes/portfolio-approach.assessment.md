# Разбор подхода к портфелю: что ложится, что расширить, что противоречит; доработки OpenClaw

Основание: `portfolio-approach.summary.md` (вырезка переписки), текущее состояние дозора (STATUS.md,
точка 20.09). Автор разбора: Claude Code, 20.09.2026. Статус: предложение владельцу.

## 1. Общий вывод

Подход совместим с построенным дозором, и другая LLM пришла к тому же самому выводу сама: OpenClaw —
операционный слой, поверх него слой интерпретации и расчётов. Из четырёх принятых здесь решений
(реестр как единственный дом триггеров, «триггер ≠ решение», проверка фактов по первоисточникам,
маршруты и типы сообщений) ни одно не противоречит Constitution. Расширять придётся в трёх местах:
вектор состояний компании, уровень портфеля, расчётный слой. Пятое решение — сценарий как пакет
действий — заменяется более сильной конструкцией «сценарий ≠ состояние».

## 2. Что уже ложится один в один

| Подход (Constitution / принципы) | У нас сейчас | Комментарий |
|---|---|---|
| Event Map с датой, источником, порогом, реакцией | triggers.yaml: condition / source / action / window | совпадает, нужны поля `level` (E1/E2/E3) и `axis` |
| Trigger ≠ Decision; Human Decision | fired.status pending_owner, owner_decision, сводка 20:00 | совпадает; расширить словарь решений |
| Evidence: unverified → verified | state.json.pending_verification (+ confirmation strong/weak) | совпадает; вынести в поле `evidence` у события |
| Приоритет источников (SEC → IR → …) | правило подтверждения в AGENTS.md, разовые проверки на Sonnet | совпадает |
| Methodology ≠ Data ≠ Interpretation | AGENTS.md + templates/ (методология), portfolio/*/ (данные), thesis.md (интерпретация) | совпадает по замыслу; методологии нужна версия и git |
| Challenger registry с условиями возврата | portfolio/_ideas.yaml (watch / ideas / rejected) | совпадает; переименовать статусы в Discovery / Candidate / Challenger |
| Фаза инвестиционного процесса | route.steps / route.current | совпадает; фаза ≠ состояние компании |
| Investment State Card | карточка по тикеру | совпадает по идее; добавить вектор состояний и цвета KPI |
| Дешёвые детерминированные наблюдатели до вызова LLM | watch-prices.js, зоны | совпадает, другая LLM предлагает сделать эталоном |

## 3. Что требует расширения (по убыванию приоритета)

1. **Портфель как сущность.** Файл `portfolio/_portfolio.yaml`: позиции (тикер, количество, валюта),
   кэш и резерв, NAV по датам, целевые веса, ограничения (§28 Total Wealth: недвижимость вне equity,
   GLD не обязателен, dry powder в cash/T-bills). Без него невозможны: просадка портфеля от максимума
   NAV, влияние события на портфель, карта портфеля, ребалансировка, Stress/Shock-режимы.
   Одновременно закрывает вопрос WAR-ECONOMY «от чего считать –35%» определениями §12.
2. **Вектор состояний компании.** В state.json — `scenario_state` (оси → текущее состояние, дата,
   evidence) и журнал `state_transitions`. В triggers.yaml у -E-/-X- триггеров — `axis` и
   `transition: {from, to}`; `action` остаётся текстом Decision Request. Оси и состояния описываются в
   новом файле компании `states.yaml` (оси, список состояний, условия переходов с числами и источниками).
   Для SpaceX оси уже названы (AI compute, Starlink, Starship, капиталоёмкость, valuation).
3. **KPI с тремя порогами.** `kpis.yaml` на компанию: KPI, единица, период, источник, формула, пороги
   Green/Yellow/Red, последнее значение. Проверка по отчёту обновляет значения и цвета; карточка и
   Decision Request показывают цвета. Наши -E-/-X- условия — частный случай (Green и Red).
4. **Уровни событий E1/E2/E3 и модельные триггеры.** Поле `level` в реестре: E1 → info_log и сводка
   (уже есть как [СПРАВОЧНО]); E2 → Decision Request с проверкой перехода состояния; E3 → запуск
   расчёта. Третий тип триггеров (implied CAGR < X, P(loss>30%) > Y, концентрация сценариев) появится
   только вместе с расчётным слоем.
5. **Расчётный слой.** Детерминированные скрипты: reverse valuation, условный Монте-Карло 3/5/8Y,
   оптимизатор, тесты устойчивости; входы и выходы — JSON с версией модели и seed. В контейнере
   OpenClaw нет numpy/pandas/scipy и нет pip — движок либо живёт на хосте (Python 3.12) и вызывается
   мной или по расписанию, либо в контейнер добавляется образ с библиотеками. Рекомендация: начать на
   хосте, результаты класть в `portfolio/<тикер>/runs/` и `portfolio/_runs/`, агент читает их как данные.
6. **Словарь решений владельца.** Сейчас «сделано / отложено / отклонено» описывает исполнение
   предложенного действия. Добавить решение по состоянию: KEEP / INCREASE / REDUCE / WAIT / EXIT
   (по-русски: держать / увеличить / сократить / ждать / выйти) с записью в `decision_records` и
   обязательной ссылкой на триггер и факт (Decision Traceability).
7. **Циклы вселенной.** Календарные задания уровня портфеля: Discovery раз в 6 месяцев, годовой
   полный review allocation, квартальный competitive review Core ↔ Challenger; в сводку —
   «Challenger gap». Еженедельная карта портфеля (тип сообщения из варианта C) становится реальной
   после пункта 1.
8. **Версионирование.** Workspace агента под git (репозиторий уже инициализирован, коммитов нет):
   методология (AGENTS.md, templates/, Constitution) меняется только версией; снапшоты компаний не
   переписываются задним числом.

## 4. Где есть противоречие или напряжение

- **Два разных портфеля из двух переписок.** Переписка о портфеле оперирует Core-10 (AVGO, NVDA,
  KLAC, ASML, SNPS, CDNS, MSFT, SPCX, RKLB, NBIS) и восемью челленджерами; в дозоре заведена корзина
  «ИИ-инфраструктура» (ETN, SU, NET, 6506, 6324, CRWD) и SpaceX. Пересечение: SPCX, NET, CRWD;
  SU у них вынесена в отдельную вселенную; ETN, Yaskawa, Harmonic Drive там отсутствуют. Это не
  ошибка ни одной из систем, а нерешённый вопрос владельца: **какой список является портфелем
  учёта**, а что — челленджеры/идеи. Пока он не решён, портфельные расчёты невозможны.
- **Действие в триггере.** У нас `action` — дословная рекомендация из стратегии («удвоить транш»);
  подход требует «триггер → переход → запрос решения» без заранее вшитого инвестиционного вывода.
  Компромисс, предложенный самой LLM, разумен: `action` остаётся как текст Decision Request и
  legacy-ссылка на стратегию, решение принимает владелец, а модельная часть (переход, влияние)
  добавляется рядом. Для ценовых траншей (DCA) `action` остаётся как есть — это дисциплина исполнения,
  не вывод модели.
- **Ценовые цели сценариев A/B/C и уровни фиксации по капитализации.** Подход считает их обратной
  логикой (сценарий → модель → implied price, а не price → сценарий). Оставить в реестре как
  legacy с пометкой до появления valuation-модели, из активного дозора не удалять: молчаливая потеря
  условия хуже лишнего напоминания.
- **Сценарий как пакет действий (наш taiwan.yaml)** vs «Taiwan shock определяется наблюдаемыми
  экономическими последствиями, а не политическим событием». Наш файл задаёт признаки стадий как
  политические/логистические факты (объявление КНР, судоходство). Согласовать: признаки наступления
  оставить (они наблюдаемы), но действия по позициям превратить в Decision Request после обновления
  вектора состояний, а не в готовые проценты продажи.
- **Сложность.** Пять осей × 4–5 состояний × Монте-Карло × оптимизатор для частного инвестора с
  10–18 бумагами — реальный риск утонуть в методологии. Защита: принцип самой переписки «SPCX как
  первый и единственный тестовый объект до тех пор, пока человек может пройти цепочку назад»;
  расширять на следующую компанию только после того, как карточка SPCX с вектором состояний
  прожила хотя бы один отчёт.
- **Два дома у методологии.** ChatGPT-проект хранит Constitution/Schema/Templates, OpenClaw —
  AGENTS.md и шаблоны. Нужен один нормативный дом: предлагаю файлы методологии держать в workspace
  агента под git (`methodology/`), ChatGPT-проект использовать как место обсуждения, а изменения
  вносить версиями.
